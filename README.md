# UpdateHub

Сервер обновлений для закрытого контура. Раздаёт файлы из одной папки на машины
под Ubuntu, которые обращаются к нему bash-скриптом и сверяются по контрольным
суммам MD5.

## Как это устроено

Сервер собирается на машине с интернетом, переносится в закрытый контур образом
Docker и разворачивается там в Docker Desktop. Папку Windows с раздаваемыми
файлами пробрасывают внутрь контейнера. Клиенты обновляют одну папку —
`/home/data`.

```
Windows-папка ──проброс──► /app/files ──обход по таймеру──► манифест в SQLite
                                                                  │
                                              сравнение с манифестом клиента
                                                                  │
   bash-скрипт ──md5sum своей папки──► POST /sync/diff ──► план: что скачать
               ◄──список файлов в формате md5sum──────────────────┘
               ──GET /files?path=...──► файл с поддержкой докачки
```

### Почему опрос, а не наблюдение за файловой системой

События inotify не проходят через проброс папки Windows в Linux-контейнер.
`FileSystemWatcher` внутри контейнера не сработал бы ни разу, и манифест
остался бы таким, каким его построили при запуске. Поэтому каталог
опрашивается по таймеру.

Чтобы опрос не читал шестигигабайтный образ каждую минуту, MD5 пересчитывается
только у файлов, у которых изменились размер или время изменения. Файл,
изменённый только что, откладывается до следующего обхода: иначе в манифест
попала бы сумма наполовину скопированного файла.

### Почему формат `md5sum`

Клиент — bash-скрипт на слабой машине в закрытом контуре, где может не оказаться
`jq`. Манифест своей папки он получает командой `md5sum`, отправляет как есть,
а целостность скачанного проверяет командой `md5sum -c` по ответу сервера.
Разбора JSON в скрипте нет вообще.

Поэтому API разделён на две части:

- **клиентская** (`/api/v1/auth`, `/sync`, `/files`, `/enroll`) — отвечает текстом:
  формат `md5sum` и строки вида `ключ=значение`;
- **панель управления** (`/api/v1/admin`) — обычный JSON, закрыта ролью `Admin`.

Сама панель — приложение Blazor WebAssembly, которое отдаёт тот же сервер
по адресу `/`. Отдельный веб-сервер в закрытом контуре означал бы ещё один
образ, ещё один порт в межсетевом экране и настройку CORS. Типы запросов
и ответов панель берёт из общей библиотеки, а не описывает заново, поэтому
правка договора на сервере ломает сборку панели, а не работу администратора.

### Разграничение доступа

Пользователь работает за компьютером, только если администратор выдал ему права
на этот компьютер или на группу, в которую тот входит. Сервер никогда не заводит
компьютеры сам: обращение с неизвестным идентификатором отклоняется, а скрипт
может подать заявку на `/api/v1/enroll`, которую администратор рассмотрит.

Идентификатор компьютера — UUID из `/etc/updatehub/client-id`. Отдельно клиент
присылает отпечаток железа: после переустановки системы идентификатор меняется,
и отпечаток позволяет узнать ту же машину.

## Структура проекта

```
UpdateHub.Server/
  Api/V1/Controllers      контроллеры; клиентские отдают текст, админский — JSON
  Api/V1/DTOs             формы клиентской части: вход, заявка, смена пароля
  Application/Manifest    формат md5sum и общее состояние манифеста
  Application/Services    прикладная логика
  Application/Repositories доступ к данным поверх EF Core
  Application/BackgroundServices  обход каталога и ночная очистка
  Domain/Entities         сущности базы данных
  Infrastructure          конфигурация, база, безопасность, диагностика
  Migrations              миграции схемы базы данных
UpdateHub.Shared/         договор между сервером и панелью: запросы, ответы, перечисления
UpdateHub.Admin/          панель управления, Blazor WebAssembly
UpdateHub.Tests/          тесты xunit, повторяют структуру серверного проекта
docs/                     списки проверок, которые нельзя выполнить тестами
```

## Запуск для разработки

```
dotnet run --project UpdateHub.Server
```

Профиль `http` слушает `http://localhost:5083` и открывает Swagger. Профиль
`http-lan` слушает `0.0.0.0:5083` — нужен, чтобы подключиться с настоящей
машины Ubuntu по сети.

При старте сервер печатает сводку: окружение, каталог раздачи, путь к базе,
период опроса, адреса и состояние манифеста. **Файлы для раздачи кладите
в каталог, указанный в строке «Каталог раздачи».** По умолчанию это папка
`files` рядом с собранным приложением, то есть `bin/Debug/net10.0/files`.

Учётные данные администратора для разработки заданы в
`appsettings.Development.json` — `admin` / `admin12345`.

## Развёртывание в закрытом контуре

На машине с интернетом, из корня репозитория:

```
make package
```

Перенести `updatehub-server.tar` и `Makefile` на целевую машину:

```
make load
make run JWT_SECRET="<ключ>" FILES_DIR=/c/updatehub/files
make logs
```

Ключ подписи генерируется командой `openssl rand -base64 48`. Без него сервер
осознанно не стартует. Пароль администратора при первом запуске выводится в лог.

Про адреса: внутри контейнера приложение обязано слушать все интерфейсы
(`ASPNETCORE_URLS=http://+:8080`) — иначе проброс порта не работает. Доступ
снаружи ограничивается параметром `-p`, а не настройкой приложения.

**База данных живёт на именованном томе Docker, а не в проброшенной папке.**
Блокировки файлов через 9p/virtiofs работают неправильно и приводят
к повреждению базы SQLite.

## Миграции

Схема применяется миграциями. Следующую заводить так:

```
dotnet ef migrations add <Название> --project UpdateHub.Server
```

База, созданная прежней версией сервера без миграций, подхватывается при
старте: журнал миграций заводится, первая миграция отмечается применённой,
данные остаются на месте. Отдельных действий это не требует, но в журнале
появляется предупреждение — так и должно быть.

Забыть миграцию не получится: тест сверяет снимок модели с сущностями
и падает, если они разошлись. Второй тест сравнивает схему из миграции
со схемой, построенной напрямую по модели, — столбец за столбцом.

## Тесты

```
dotnet test
```

Тесты работают с настоящим SQLite, а не с поставщиком InMemory: последний
не выполняет SQL и потому не проверяет ни уникальные индексы, ни каскадные
удаления, ни трансляцию запросов.

Тесты контроллеров поднимают приложение целиком через `WebApplicationFactory`:
настоящая маршрутизация, привязка формы, проверка токена и подготовка базы,
включая применение миграций. Опечатка в маршруте или забытый атрибут роли
не видны ни компилятору, ни тестам служб — только такому прогону.

Чего тесты не проверяют и проверить не могут: поведение проброшенной с Windows
папки, отдачу шестигигабайтного файла по узкому каналу и блокировки SQLite
под нагрузкой. Для этого есть список проверок вручную —
[docs/proverka-v-docker.md](docs/proverka-v-docker.md), проходится один раз
на целевой машине.
