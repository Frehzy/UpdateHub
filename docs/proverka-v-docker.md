# Проверка развёртывания в Docker

Список проверок, который нужно пройти один раз на целевой машине — Windows
с Docker Desktop и проброшенной папкой. Всё, что можно было проверить тестами,
уже проверено ими; здесь остаётся то, что зависит от самой машины: поведение
проброшенной папки, права, блокировки файла базы и скорость обхода каталога.

Проверки идут по порядку: каждая следующая опирается на предыдущую.
Для каждой указано, что означает неуспех и что делать.

---

## 0. Подготовка

```bash
cd UpdateHub.Server
make package                          # на машине с интернетом
```

Перенести `updatehub-server.tar` и `Makefile` на целевую машину, затем:

```bash
make load
make run JWT_SECRET="<ключ>" FILES_DIR=/c/updatehub/files
```

Ключ получить командой `openssl rand -base64 48`. Путь к папке указывается
в формате `/c/...`, а не `C:\...`.

---

## 1. Контейнер поднялся и остался жив

```bash
docker ps
```

**Ожидается:** контейнер `updatehub-server` в состоянии `Up`, через полторы
минуты — `Up (healthy)`.

**Если `Restarting`:** смотреть `make logs`. Наиболее вероятные причины —
не задан `Jwt__SecretKey` (сервер отказывается стартовать намеренно) или
каталог базы недоступен на запись.

---

## 2. Схема базы создана миграцией, а не по модели

```bash
make logs | grep -i "миграц\|схем"
```

**Ожидается:** `Применение миграций: 20260816140000_Initial`.

**Если видно `Миграции не найдены, схема создаётся по модели`** — в образ
не попала сборка с миграциями; пересобрать образ.

**Если база осталась от прежней версии сервера**, ожидается строка
`База создана без миграций. Миграция ... отмечается как применённая`.
После неё учётные записи и история обязаны остаться на месте — проверяется
на шаге 9.

---

## 3. Пароль первого администратора выдан один раз

```bash
make logs | grep -i "администратор"
```

**Ожидается:** строка с логином и паролем (либо сообщение, что пароль взят
из конфигурации). Пароль записать: повторно узнать его нельзя.

Смена пароля обязательна при первом входе.

---

## 4. Сервер отвечает и виден по сети

```bash
curl http://localhost:8080/health
curl http://localhost:8080/
```

**Ожидается:** `Healthy` и текстовая справка по адресам.

Затем то же самое **с другой машины сети**, по адресу целевой машины:

```bash
curl http://<адрес сервера>:8080/health
```

**Если изнутри работает, а снаружи нет:** порт проброшен (`-p 8080:8080`),
значит дело в брандмауэре Windows — разрешить входящие на 8080.

---

## 5. Каталог раздачи проброшен и читается

Положить в папку Windows пробный файл:

```bash
echo -n hello > /c/updatehub/files/proverka.txt
```

Изнутри контейнера:

```bash
docker exec updatehub-server ls -l /app/files
docker exec updatehub-server md5sum /app/files/proverka.txt
```

**Ожидается:** файл виден, сумма `5d41402abc4b2a76b9719d911017c592`.

**Если `Permission denied`:** контейнер работает от uid 1000, а папка Windows
отдаётся с правами, заданными Docker Desktop. Проверить, что папка добавлена
в *Settings → Resources → File sharing*.

---

## 6. Обход каталога подхватывает изменения без перезапуска

Это ключевая проверка всей затеи с опросом.

```bash
# войти и получить токен
curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -d username=admin -d password='<пароль>' | tee /tmp/tokens.txt

TOKEN=$(grep ^access_token= /tmp/tokens.txt | cut -d= -f2)

curl -s -H "Authorization: Bearer $TOKEN" \
  http://localhost:8080/api/v1/admin/manifest/status
```

Затем положить в папку новый файл, подождать **больше минуты** (опрос идёт раз
в 60 секунд, плюс 15 секунд выдержки на дописывание) и запросить состояние
снова.

**Ожидается:** `entryCount` вырос, `generation` увеличилось.

**Если не меняется** — обход не видит проброшенную папку. Это тот самый случай,
ради которого выбран опрос вместо подписки на события: события файловой системы
через 9p/virtiofs из Windows в контейнер не доходят. Если не работает и опрос,
проверить шаг 5 и посмотреть `make logs` на предмет ошибок обхода.

Внеочередной обход по требованию:

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:8080/api/v1/admin/manifest/rescan
```

**Ожидается:** `{"status":"ok", ...}` с числом файлов.

## 7. Большой файл отдаётся целиком и докачивается

Проверка ради образа `astra176.iso` — около шести гигабайт. Положить его
в папку раздачи, дождаться обхода (шаг 6), затем:

```bash
# завести компьютер и выдать права
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"clientId":"pc-proverka"}' http://localhost:8080/api/v1/admin/clients

# скачать с ограничением скорости и оборвать на середине
curl --limit-rate 2M -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8080/api/v1/files?client_id=pc-proverka&path=astra176.iso" \
  -o /c/updatehub/proverka.iso
# прервать через минуту сочетанием Ctrl+C

# докачать с прерванного места
curl -C - --limit-rate 2M -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8080/api/v1/files?client_id=pc-proverka&path=astra176.iso" \
  -o /c/updatehub/proverka.iso

md5sum /c/updatehub/proverka.iso
```

**Ожидается:** докачка продолжается с прерванного места (curl показывает
ненулевой начальный отступ), итоговая сумма совпадает с суммой исходного файла.

**Если докачка начинается с нуля:** сервер не отдал `Accept-Ranges` либо ETag
изменился между попытками. Проверить, что файл в папке не менялся.

**Отдельно проверить, что отдача не обрывается по таймауту.** На канале
2 Мбит/с шесть гигабайт идут около семи часов; ограничения Kestrel на
минимальную скорость сняты именно поэтому. Достаточно оставить закачку
с `--limit-rate 200k` на полчаса и убедиться, что она не прервалась.

## 8. База не портится под нагрузкой

Самая важная проверка: файл базы обязан лежать на именованном томе, а не
в проброшенной папке.

```bash
docker inspect updatehub-server --format '{{json .Mounts}}'
```

**Ожидается:** `/app/data` — том (`"Type":"volume"`), `/app/files` — папка
(`"Type":"bind"`).

**Если `/app/data` оказался bind-монтированием в папку Windows** — вернуть том.
Блокировки файлов через 9p/virtiofs работают неправильно, и база рано или
поздно повредится.

Затем нагрузить одновременными обращениями:

```bash
for i in $(seq 1 20); do
  curl -s -H "Authorization: Bearer $TOKEN" \
    "http://localhost:8080/api/v1/sync/manifest?client_id=pc-proverka" > /dev/null &
done
wait

make logs | grep -i "database is locked"
```

**Ожидается:** ни одной строки про блокировку.

---

## 9. Данные переживают перезапуск

```bash
make restart
make logs | grep -i "администратор"
```

**Ожидается:** сообщения о создании администратора **нет** — учётные записи
на месте. Вход прежним паролем работает.

Затем убедиться, что миграции не применяются повторно:

```bash
make logs | grep -i "миграц\|актуальна"
```

**Ожидается:** `Схема базы данных актуальна`.

## 10. Полный проход клиентского сценария

С машины Ubuntu, тем же способом, каким будет работать скрипт:

```bash
# 1. заявка на регистрацию (без учётных данных)
curl -s -X POST http://<сервер>:8080/api/v1/enroll \
  -d client_id=pc-test -d hostname=$(hostname) -d os_version="$(uname -r)"

# 2. администратор одобряет заявку и выдаёт права пользователю

# 3. вход
curl -s -X POST http://<сервер>:8080/api/v1/auth/login \
  -d username=<логин> -d password=<пароль> -d client_id=pc-test

# 4. сравнение манифестов
cd /home/data && find . -type f -printf '%P\n' | xargs -r md5sum > /tmp/my.txt
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: text/plain' \
  --data-binary @/tmp/my.txt \
  "http://<сервер>:8080/api/v1/sync/diff?client_id=pc-test"
```

**Ожидается:** ответ вида

```
@GENERATION 3
@STATUS update
@COUNT 2
@SIZE 6442450944
5d41402abc4b2a76b9719d911017c592  docs/proverka.txt
...
```

Строки файлов разбираются обычным `while read hash path`, без jq.
