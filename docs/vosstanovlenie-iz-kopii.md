# Восстановление базы из резервной копии

Порядок на случай, когда база испорчена, потеряна вместе с томом Docker или
нужно откатиться к состоянию на вчера.

Читать это лучше **до** того, как понадобится. Восстановление не сложное, но
одна его часть неочевидна и в спешке пропускается — про журналы WAL, пункт 4.

## Что вообще есть

Сервер снимает копию базы раз в сутки и хранит последние семь. Каталог копий —
проброшенная папка Windows, `make run` монтирует её как `/app/backup`:

```
docker run ... -v "<папка>/backup":/app/backup ...
```

Копии называются `updatehub-ГГГГММДД-ЧЧММСС.db`, время в UTC. Каждая — целая
база SQLite, не архив и не приращение: её можно открыть чем угодно, хоть
`sqlite3`, и восстановление сводится к подстановке файла на место рабочего.

**Что в копии есть:** учётные записи, права, группы, компьютеры, история
обращений и изменений, заявки на регистрацию.

**Чего в копии нет:** самих раздаваемых файлов. Они лежат в каталоге раздачи
и копируются отдельно, вашими обычными средствами. Потеря базы не задевает их,
а потеря их не задевает базу.

## Что проверить перед началом

Состояние копирования видно в панели управления, раздел «Резервная копия базы»,
или запросом `GET /api/v1/admin/maintenance`. Посмотрите **дату последней
удачной копии** — если копирование отказывало неделю, самая свежая копия
недельной давности, и это надо знать до, а не после.

## Порядок восстановления

### 1. Остановить сервер

```
docker stop updatehub
```

Пока он работает, файл базы менять нельзя: часть записей у него в памяти
и в журнале, и подмена файла под работающим сервером испортит и то и другое.

### 2. Выбрать копию

```
dir <папка>\backup
```

Берите нужную по дате в имени. Если восстанавливаетесь после порчи — самую
свежую; если откатываетесь после ошибочного действия — последнюю **до** него.

### 3. Сохранить то, что есть сейчас

```
copy <папка>\backup\na-vsyakiy-sluchay-<дата>.db
```

Скопируйте текущую базу из тома куда-нибудь в сторону, даже если считаете её
испорченной. Стоит это ничего, а вернуться к ней иногда всё-таки нужно —
например, если окажется, что беда была не в базе.

Достать файл из тома можно так:

```
docker run --rm -v updatehub-data:/data -v "<папка>":/out alpine ^
    cp /data/updatehub.db /out/na-vsyakiy-sluchay.db
```

### 4. Удалить старую базу вместе с журналами

Это тот пункт, который пропускают.

```
docker run --rm -v updatehub-data:/data alpine ^
    sh -c "rm -f /data/updatehub.db /data/updatehub.db-wal /data/updatehub.db-shm"
```

Файлы `-wal` и `-shm` — журнал предзаписи SQLite и его разделяемая память.
Если оставить их рядом с восстановленным файлом, SQLite при открытии попытается
применить к нему незаписанные страницы **от прежней базы**. Получится смесь
двух состояний, и это хуже, чем обе исходные по отдельности.

### 5. Положить копию на место рабочей базы

```
docker run --rm -v updatehub-data:/data -v "<папка>\backup":/backup alpine ^
    cp /backup/updatehub-20260817-030000.db /data/updatehub.db
```

Имя обязано быть ровно `updatehub.db` — его ищет сервер (настройка
`UpdateHub__DatabasePath`).

### 6. Запустить сервер и посмотреть вывод

```
docker start updatehub
docker logs -f updatehub
```

Правильный вывод выглядит так:

```
info: Схема базы данных актуальна
info: SQLite переведён в режим WAL
Сервер обновлений UpdateHub запущен
  ...
```

**Чего быть не должно:**

- `ПЕРВЫЙ ЗАПУСК. Создана учётная запись администратора` — значит сервер счёл
  базу пустой. Вы подставили не тот файл либо он не открылся; вернитесь к пункту 5.
- `Применение миграций` при восстановлении копии от этой же версии сервера —
  значит копия снята более старой версией. Это нормально, миграции применятся,
  но запишите себе, что версии разошлись.
- `База создана без миграций` — копия снята очень старой версией; сервер её
  подхватит, но проверьте данные внимательнее.

### 7. Проверить, что вернулось

Войдите в панель и посмотрите: список компьютеров, список пользователей, их
права. Затем на любой машине выполните `updatehub sync` — обновление должно
пройти обычным порядком.

## Чего восстановление не вернёт

Токены обновления, выданные **после** снятия копии, в ней отсутствуют. Машины,
получившие их за это время, при следующем запуске получат отказ на обновлении
токена и **сами войдут по паролю** из своего файла настроек — вмешательства
не требуется, при условии, что `USERNAME` и `PASSWORD` там заполнены.

История обращений между снятием копии и восстановлением потеряна. На работу
это не влияет, но сводка за этот промежуток будет пустой.

## Если копий нет вообще

Сервер поднимется на пустой базе и заведёт администратора заново, напечатав
логин и пароль при старте. Всё остальное придётся заводить руками: пользователей,
компьютеры, группы, права. Раздаваемые файлы при этом не теряются, а машины
после выдачи прав продолжат обновляться — идентификатор компьютера хранится
у них в `/etc/updatehub/client-id` и не меняется.

Именно поэтому стоит смотреть на дату последней удачной копии в панели, а не
узнавать о её отсутствии в этот момент.
